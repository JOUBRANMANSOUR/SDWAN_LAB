## Mandatory end-to-end model

Implement and document this complete control loop:

```text
six pre-established spoke tunnels
        ↓
continuous local health measurements
        ↓
tunnel and hub state machines
        ↓
application-selected transport slot
        ↓
healthy hub-specific target resolution
        ↓
versioned route ownership
        ↓
atomic Linux route/rule update
        ↓
symmetric forward and return path
        ↓
failure event and state reconciliation
        ↓
hysteretic recovery and controlled failback
```

The data-plane decision has two separate dimensions:

```text
transport slot = MPLS / Broadband / LTE
hub target     = hub1 / hub2
```

nDPI produces application metadata only.
It must not select the SLA class, transport, hub or route.

The Policy Service maps:
application/category → SLA class → allowed and ranked transports.

The Edge selects the first locally healthy eligible target while respecting
the current versioned policy.

The edge route resolver combines:

- the flow's application/SLA transport preference;
- the locally observed tunnel state;
- the locally observed hub state;
- the latest valid central policy;
- current route ownership;
- failover and hold-down state;

to select one stable hub/transport target for the flow.

## Mandatory dual-hub tunnel invariant

Every spoke must have exactly one pre-established tunnel for every
`hub × transport` pair:

| Hub | MPLS | Broadband | LTE |
|---|---|---|---|
| hub1 | `wg-h1-mpls` | `wg-h1-bb` | `wg-h1-lte` |
| hub2 | `wg-h2-mpls` | `wg-h2-bb` | `wg-h2-lte` |

All six tunnels must be configured, up, peer-validated and monitored before a
spoke is declared ready. A standby tunnel is a hot standby data-plane object,
not an unconfigured template.

Failover must normally change Linux route selection to an already established
tunnel. It must not create a tunnel or change a WireGuard endpoint in the
failure path.

## Mandatory route-ownership model

Do not treat route ownership as an informal side effect of `ip route`.

Create an explicit versioned ownership record for every spoke LAN prefix. At
minimum, the model must include:

```text
prefix
spoke
preferred_hub
standby_hub
current_owner_hub
previous_owner_hub
owner_epoch
policy_version
route_version
state
reason
updated_at
valid_until or staleness information
pending_reconciliation
```

Required invariants:

1. Exactly one hub is the authoritative owner of a spoke LAN prefix during
   normal converged operation.
2. Both hubs may have pre-established WireGuard peers, but they must not both
   advertise or install equal authoritative forwarding for the same prefix
   without an explicitly designed and tested multipath mode.
3. A non-owner hub must either route the prefix toward the owner through a
   healthy inter-hub path or use a documented emergency direct-standby rule.
4. A failed direct tunnel must never remain preferred over a healthy owner or
   inter-hub route.
5. Ownership changes must be monotonic by `owner_epoch`; stale events,
   duplicated events and out-of-order updates must not restore an old owner.
6. Route state must be idempotent and reconstructable after process restart.
7. A route must record why it is installed and which policy/ownership version
   produced it.

Define one component as the authoritative writer of central ownership state.
The recommended choice is the SD-WAN policy service. Ryu is not the route
ownership database.

The edge agent owns local Linux actuation. The policy service owns global
intent and ownership coordination. Each component must reject state outside
its responsibility.

Static routes must mean dynamically managed Linux route entries generated from persistent desired state, continuously reconciled by the edge agent, transactionally replaced during failure and recovery, protected against stale versions and reconstructed after restart; they must never be implemented as one-time route configuration performed only when the topology starts.

## Mandatory ownership-transition sequence

Implement ownership transfer as a state machine, not as three unrelated REST
calls.

For a transfer from `hub1` to `hub2`, use a safe sequence equivalent to:

```text
1. create a new ownership epoch;
2. verify that hub2 and the required spoke-to-hub2 tunnels are usable;
3. prepare hub2 routes without yet accepting stale lower-epoch state;
4. switch the spoke's affected local route targets atomically;
5. make hub2 the authoritative owner;
6. update remote-hub forwarding toward hub2;
7. withdraw or demote hub1's stale direct route;
8. verify forward and return reachability;
9. commit the ownership epoch;
10. record unreachable components for later reconciliation.
```

The exact order may be adjusted when needed to avoid a black hole, but the code
must document its safety invariant and test every intermediate state.

The failed old hub must not be a commit dependency. If it is unreachable:

- continue with the surviving hub and spoke;
- fence the old ownership using a higher epoch;
- record pending reconciliation;
- reconcile the recovered hub before it can forward as owner again.

Rollback is allowed only to a proven usable state. Never roll back to a hub
that is still failed merely because an acknowledgement timed out.

## Mandatory local-failover behavior

Local failover has two distinct scopes and both must be implemented:

1. `local egress convergence`: the spoke immediately changes the affected
   route target using cached policy and local health.
2. `network-wide destination convergence`: hubs update route ownership so
   traffic from other spokes reaches the moved spoke through the correct hub.

Do not claim full failover after only local egress convergence has succeeded.

Local egress failover must:

- run without waiting for Ryu or a controller round trip;
- serialize concurrent failover operations;
- use a local monotonic route version;
- use atomic or transactional `ip route`/`ip rule` replacement;
- preserve the previous confirmed state for safe rollback;
- verify the selected interface, peer and next hop;
- emit an idempotent event with site, slot, old target, new target, reason,
  local route version and timestamp;
- continue forwarding with the latest valid cached policy when the policy
  service is unavailable.

The policy service must later reconcile local emergency state with global route
ownership. It must not overwrite a newer local emergency route with stale
central state.

If central coordination is unavailable, define the exact safe degraded mode.
Do not imply that one spoke's local route change alone can guarantee inbound
reachability from every other spoke.

## Mandatory symmetry and return affinity

Symmetry must cover both dimensions:

```text
transport affinity + hub affinity
```

The existing low route-mark byte identifies only the transport slot. By
itself, it cannot distinguish:

```text
hub1/Broadband
from
hub2/Broadband
```

Therefore, inspect the v4 mark layout and implement a collision-free mechanism
that preserves the existing transport ABI while also preserving hub/target
affinity where required. A valid design may use:

- additional non-overlapping `CONNMARK` bits for hub/target identity;
- conntrack labels plus masked policy-routing rules;
- hub-specific routing tables selected by an extended mark;
- another documented connection-aware mechanism.

Whichever design is chosen, document:

- every bit mask;
- every routing table;
- restore/save masks;
- rule priority;
- how forward and reverse tuples share one connection decision;
- how locally generated reply traffic is handled;
- how fragments and retransmissions retain affinity;
- how old marks are cleared during cleanup;
- how compatibility with v4 marks is preserved.

Do not silently overload `0x100`, `0x200` or `0x400`. Do not allow hub bits to
leak into the `0xff` transport mask.

Required symmetry invariant:

> A flow that enters a spoke or hub through a particular hub/transport target
> must return through the corresponding target for the life of the healthy
> flow, unless a hard failure makes that target unusable.

Test symmetry using packet capture on both candidate tunnels and by inspecting
conntrack state. Test at least TCP and UDP in both directions.

## Mandatory route-table design check

Do not assume that changing only tables `101`, `102` and `103` is sufficient
for every failback policy.

A single table per transport can perform slot-wide emergency remapping, but it
cannot simultaneously guarantee both:

- old flows remain on the backup hub; and
- new flows immediately return to the recovered preferred hub.

Choose and document one coherent implementation:

### Baseline acceptable design

- use slot-wide emergency remapping;
- keep both existing and new flows on the backup target;
- wait for active flows to drain or for a configured timeout;
- then restore the slot to the preferred target atomically.

### Enhanced design

- add connection-level hub/target affinity and separate hub-specific route
  tables or equivalent state;
- keep existing flows pinned to the backup target;
- assign new flows to the recovered preferred target;
- remove backup state only after the old flow cohort drains.

Do not claim new-flow-first failback while implementing only a single mutable
table per transport. State in `ARCHITECTURE.md` which design was selected and
why. Add tests that prove the claimed behavior.

## Mandatory monitoring model

Monitoring must be active for every preferred, standby and inter-hub tunnel,
not only for the current route target.

Separate raw observations from derived state:

```text
raw measurements
    ↓
freshness validation
    ↓
tunnel state machine
    ↓

    ↓
route resolver
```

One failed tunnel may degrade a hub but must not automatically mark the entire

Every measurement must identify:


Reject stale samples. Do not let an old successful probe override a newer

Handshake age is supporting evidence, not a complete liveness test. An idle

## Mandatory recovery and failback model

Recovery is not the inverse of failure executed immediately.

Implement:

```text
FAILED
  -> RECOVERING
  -> HEALTHY_CANDIDATE
  -> eligible after hold-down and validation
  -> controlled failback
```

Equivalent state names are allowed, but one successful probe must never cause
immediate failback.

Before failback, verify:

- physical and underlay reachability;
- WireGuard interface and expected peer;
- recent handshake when traffic/probes are present;
- overlay reachability;
- required SLA;
- consecutive recovery successes;
- non-stale policy and ownership epoch;
- absence of a conflicting manual override;
- hub capacity for the returning load;
- symmetric forward and reverse path;
- completed hold-down.

Failback must be separately configurable as:

- manual;
- automatic after drain;
- automatic after timeout;
- enhanced new-flow-first mode, but only if per-flow hub affinity exists.

Repeated failures must extend the hold-down. A recovered old hub must reconcile
to the newest ownership epoch before any route through it becomes
authoritative.

## Mandatory inter-hub partition safety

Choose and implement one explicit strategy for total inter-hub failure.

The recommended v5 research strategy is deterministic temporary convergence:

1. select one healthy convergence hub using a configured deterministic rule
   and capacity validation;
2. move the affected spokes to their already established tunnels to that hub;
3. transfer route ownership under one new epoch;
4. verify all-spoke forwarding and symmetry;
5. keep the other hub fenced from authoritative ownership until inter-hub
   recovery and reconciliation.

If a different strategy is chosen, justify it and prove that it prevents loops,
duplicate ownership and asymmetric black holes.

State the coordination assumption explicitly. If all inter-hub data paths and
the policy/management coordination path fail simultaneously, safe global
ownership and uninterrupted cross-group reachability may be impossible to
guarantee. In that partition:

- prefer a deterministic fail-safe state over split-brain forwarding;
- preserve reachable local traffic;
- report degraded/partitioned state;
- never invent a successful global convergence result;
- test and document the exact limitation.

## Automatic rejection conditions

Reject the implementation as incomplete if any of the following is true:

- a spoke has fewer than six configured and validated hub/transport tunnels;
- standby tunnels are not continuously monitored;
- failover creates a new tunnel in the critical path;
- one failed tunnel marks an otherwise reachable hub completely down;
- route ownership is represented only by an unversioned `active_hub` string;
- stale or duplicate events can reverse a newer route;
- local egress switches but remote route ownership remains permanently stale;

- Ryu is placed in the nDPI, WireGuard or Linux policy-routing decision loop;
- Windows-only tests are reported as proof of Ubuntu networking behavior;
- `sdwan_v4` changes.

Implement a lightweight secure zero-touch onboarding architecture inspired by
RFC 8572 and its RFC 9646 CSR extension.

Use the standards for their security and lifecycle principles:

- pre-established bootstrap trust;

- protected configuration delivery;
- replay protection;
- explicit progress and completion reporting;
- revocation;
- auditability.

The selected research design must remain lighter than a production SZTP,
BRSKI/MASA, TPM, HSM or distributed-PKI deployment.

Document the evidence boundary accurately:

- TeraFlowSDN is relevant implementation evidence for separate ZTP,
  OpenFlow/Ryu-domain integration and persistent context, but it does not

- no source should be claimed to implement the complete combination unless it

## Mandatory ZTP architecture

Implement this logical architecture:

```text
generic unclaimed edge container
        │
        │ device UUID
        │ one-time claim
        │ pinned bootstrap CA
        │ generic ZTP URL
        ▼

        ├── authenticates bootstrap identity

                    ▼

        ├── loads the administrator-staged site profile
```

## Administrator intent versus runtime decisions

The administrator must define declarative intent once, in validated
configuration or through an authenticated administrative API.

Examples:

```text
device UUID X is assigned to node1
node1 owns LAN prefix 10.1.0.0/24
node1 prefers hub1
node1 uses hub2 as standby
node1 uses the standard-branch application policy
```

Do not hard-code these decisions in Python conditionals such as:

```text
if site in node1,node2,node3: use hub1
else: use hub2
```

Store the decisions as inventory/site-profile data.

The administrator does not re-enter them during every topology launch or
enrollment. ZTP authenticates the device and retrieves its existing profile.

The runtime system must decide automatically:

- individual overlay addresses;
- listen ports;
- WireGuard peers;
- `AllowedIPs`;
- routing-table contents;
- desired-state versions;
- current route owner;
- current healthy hub/transport target;
- failover;
- recovery;
- failback.

The device must never be trusted merely because it asserts:

```text
site = node1
preferred_hub = hub1
lan_prefix = 10.1.0.0/24
```

Site identity and ownership must come from trusted inventory associated with
the authenticated bootstrap identity.

## Mandatory incremental enrollment

Replace the v4 all-router batch registration model.

Do not require one request containing a public key for every router.

Support independent, idempotent enrollment:

```text
hub1 enrolls
hub2 enrolls
node1 enrolls
node2 enrolls
...
```

Requirements:

- one failed enrollment must not block unrelated devices;
- hubs must be able to enroll before spokes;
- a spoke may wait in `PENDING_HUBS` until both hubs are prepared;
- duplicated enrollment events must be idempotent;
- the same authenticated device may resume an interrupted enrollment;
- a different device may not take over an existing site without an authorized
  replacement workflow;
- restarting a service must not cause all devices to enroll again.

## Mandatory hub-first provisioning transaction

For every new spoke:

1. Authenticate the bootstrap identity.
2. Validate and atomically consume the claim.
3. Assign the staged site profile.
4. Validate device capabilities.
5. Register the device operational certificate.
6. Accept only WireGuard public keys.
7. Transactionally reserve all hub/transport addresses and ports.
8. Generate a new desired-state version and ownership epoch.
9. Prepare hub1 with the new spoke peers/routes.
10. Verify hub1 exact applied state.
11. Prepare hub2 with the new spoke peers/routes.
12. Verify hub2 exact applied state.
13. Deliver the spoke desired state.
14. Apply all six spoke interfaces.
15. Validate exact peers, addresses, ports and `AllowedIPs`.
16. Run active overlay probes to both hubs on all required transports.
17. Validate policy routing, marks, CONNMARK and classifier readiness.
18. Activate normal route ownership.
19. Mark the site `ACTIVE`.
20. Record completion; the claim must already have become permanently
    non-reusable when certificate issuance committed.

The precise order may use prepare/commit phases, but both hubs must be safe
receivers before the spoke is activated.

# Required WireGuard topology

Each spoke must have six pre-established WireGuard interfaces:

wg-h1-mpls
wg-h1-bb
wg-h1-lte

wg-h2-mpls
wg-h2-bb
wg-h2-lte

For node1-node3:

- The hub1 interfaces are preferred.
- The hub2 interfaces are standby.

For node4-node5:

- The hub2 interfaces are preferred.
- The hub1 interfaces are standby.

All six interfaces must:

- Be created during initial reconciliation.
- Have valid peers before traffic begins.
- Be brought up continuously.
- Use persistent keepalive.
- Be monitored continuously.
- Have unique local addresses.
- Use unique listen ports where required.
- Be validated after startup.
- Remain ready so failover is a route change rather than tunnel creation.

Do not reuse the same overlay address on two WireGuard interfaces.

Use separate overlay addressing for every hub/transport combination or another validated addressing design that guarantees:

- no duplicate local addresses;
- no ambiguous connected routes;
- no WireGuard AllowedIPs collision within one interface;
- deterministic peer selection;
- deterministic Linux route selection.

WireGuard AllowedIPs act as cryptokey routing state. Do not place overlapping remote LAN prefixes on two peers of the same WireGuard interface and assume that this provides active/standby behavior.

Separate interfaces must be used where the same remote prefixes can be reached through both hubs.

The hubs must also have monitored inter-hub connectivity.

Avoid AllowedIPs overlap between:

- a direct spoke peer;
- the other hub peer;
- another spoke peer.

If necessary, use separate inter-hub WireGuard interfaces, for example:

wg-ih-bb
wg-ih-lte

- spoke-to-hub tunnels;
- hub-to-hub tunnels;
- transport identity;

# Preserve application mark semantics

Retain the current transport mark ABI unless a change is absolutely required:

0x01 = MPLS route slot
0x02 = Broadband route slot
0x03 = LTE route slot

0x100 = inline inspection terminal
0x200 = provisional inspection
0x400 = emergency remapping

The path mark should continue to represent the application-selected transport class, not a particular hub.

For example:

mark 0x02
    means Broadband route slot

The edge should resolve that slot to the currently selected hub-specific interface:

Normal node1 state:

table 101 -> wg-h1-mpls
table 102 -> wg-h1-bb
table 103 -> wg-h1-lte

After complete hub1 failure:

table 101 -> wg-h2-mpls
table 102 -> wg-h2-bb
table 103 -> wg-h2-lte

After only the hub1 Broadband tunnel fails:

table 102 -> wg-h2-bb

while tables 101 and 103 may remain on hub1.

Do not require nDPI to classify an established flow again during emergency failover.

CONNMARK must continue restoring the flow’s route slot.

Emergency tunnel or hub failover may remap the route table behind that slot because the original path is unusable.

This is different from ordinary SLA optimization:

- SLA brownout normally affects new flows.
- Hard tunnel or hub failure may move existing flows because the original path is unavailable.
- Never perform per-packet path selection.
- Prevent packet reordering whenever the old path is still usable.

# Required health monitoring

Every spoke must continuously monitor all six spoke-to-hub tunnels, including standby tunnels.

Do not monitor only the currently active hub.

# Failure-selection order

When one preferred-hub tunnel fails, use a deterministic ranked candidate list.

For example, if node1 loses wg-h1-bb:

1. Prefer wg-h2-bb if it is healthy and satisfies the application SLA.
2. Otherwise choose another healthy transport through hub1 if it better satisfies the SLA.
3. Otherwise choose another healthy transport through hub2.
4. If no candidate is healthy, report the route slot as unavailable.

Do not hard-code Broadband, MPLS or LTE as the universal backup.

Rank candidate targets using:

- application SLA class;
- transport health;
- hub health;
- delay;
- jitter;
- loss;
- estimated available bandwidth;
- path cost;
- current utilization;
- route stability;
- preference penalty;
- recent switching history.

The policy engine may provide ranked transports, but the edge must resolve the transport to a healthy hub-specific tunnel locally.

# Local failover responsibility

Fast emergency failover must occur at the edge.

It must not wait for:

- Ryu;
- a controller round trip;
- the policy service;
- a new WireGuard configuration;
- nDPI reclassification.

The edge must use:

- locally cached valid policy;
- continuously monitored standby tunnels;
- local health state;
- versioned route state;
- transactional route replacement.

After switching, the edge should notify the policy service.

If the policy service is unavailable, local traffic must continue and the event must be retried or reconciled later.

- reject stale updates;

- coordinate failback;
- support manual overrides with expiry;
- support deterministic conflict resolution;
- avoid requiring the failed hub to acknowledge before recovery proceeds.

# Correct the existing complete-hub failure weakness

The current Phase-1 failover applies state in this order:

old hub
new hub
spoke

This fails if the old hub is completely unreachable.

Replace this behavior.

For complete old-hub failure, the recovery sequence should be similar to:

1. Verify that the standby hub is reachable.
2. Prepare the standby hub to receive the affected spoke.
3. Switch the spoke route slots locally or reconcile the spoke.
4. Verify all required overlays.
5. Verify LAN-to-LAN forwarding.
6. Update the old hub only if reachable.
7. If the old hub is unreachable, record pending reconciliation.
8. Reconcile the old hub after recovery.
9. Never roll the spoke back to a confirmed failed hub merely because the old hub could not acknowledge.

Use versioned, idempotent desired state.

Rollback must be safe, but rollback must not restore an unusable old hub.

# Spoke-specific primary-hub isolation

- hub1 remains healthy.
- node2 and node3 can reach hub1.
- node1 loses all access to hub1.
- node1 can still reach hub2.

node1 -> hub2 -> hub1 -> node2

and return traffic:

node2 -> hub1 -> hub2 -> node1

    node1 LAN -> direct node1 tunnel

hub1:
    node1 LAN -> inter-hub path to hub2

Ensure that hub1 does not continue sending node1 traffic through the failed direct tunnel.

# Inter-hub failure

Continuously monitor every inter-hub tunnel.

Distinguish:

- one inter-hub transport failure;
- all inter-hub tunnels failing;
- one hub failing;
- management connectivity failing while the data plane remains healthy.

When one inter-hub transport fails:

- use another healthy inter-hub transport;
- preserve the route slot where possible;
- apply hysteresis and hold-down.

When all inter-hub tunnels fail but both hubs and all dual-attached spokes remain reachable:

- the network must not silently form two isolated spoke groups;
- use the pre-established secondary spoke-to-hub tunnels;
- select a deterministic symmetric fallback.

A valid strategy may be either:

1. Temporarily converge affected communication or spoke assignments onto one healthy hub; or
2. Use direct standby spoke tunnels from each hub with explicit route ownership and ingress return affinity.

Choose one strategy, document it and test it.

The strategy must guarantee:

- no routing loops;
- no ambiguous AllowedIPs;
- no asymmetric black hole;
- deterministic return traffic;
- no duplicate route ownership;
- recovery after the inter-hub link returns.

Do not assume that an inter-hub WireGuard peer alone automatically provides correct routing.

# Ingress return affinity

Extend the current return-affinity design across both transport and hub dimensions.

If a flow reaches node4 through:

wg-h1-bb

its return traffic must use the corresponding hub1/Broadband path unless a hard failure requires emergency movement.

Return affinity must be stored safely using conntrack/routing state.

Do not allow node4 to receive through hub1 and return through hub2 merely because hub2 is its preferred hub.

Test both TCP and UDP return symmetry.

# Existing and new flow behavior

Retain the current nDPI flow-pinning principles:

- nDPI classifies locally.
- The classifier produces application metadata.
- The policy maps application to SLA class.
- The edge selects a transport route slot.
- CONNMARK pins the established flow.
- Ordinary policy changes affect new flows.
- Do not migrate established TCP or UDP simply because nDPI finishes classification later.
- Hard tunnel/hub failure is an emergency exception because the original path cannot carry traffic.

During emergency failover:

TCP:
- may experience packet loss and retransmission;
- should continue if the application timeout is not exceeded.

UDP:
- packets lost during detection are not recovered;
- later packets should use one stable backup path.

Record:

- failure detection time;
- route switch time;
- packets lost;
- TCP retransmissions;
- flow survival;
- old and new physical tunnel;
- original route slot;
- emergency reason.

# Failback and anti-flapping

Recovery must require:

- multiple successful probes;
- valid WireGuard handshake;
- overlay reachability;
- SLA compliance;
- hold-down completion;
- no stale state;
- consistent central/local version.

Recommended behavior:

- existing flows remain on the backup when practical;
- new flows return to the preferred hub first;
- route slots are restored after active-flow drain or timeout;
- repeated up/down events extend hold-down;
- manual overrides prevent automatic failback until expiry.

Test repeated hub and tunnel flapping.

# Mandatory failover acceptance scenarios

The implementation is incomplete unless all of the following behaviors are
implemented and tested on Ubuntu:

1. Single tunnel failure

   Given node1 normally uses:
       MPLS -> wg-h1-mpls
       Broadband -> wg-h1-bb
       LTE -> wg-h1-lte

   When only wg-h1-bb fails:
       table 102 must switch to wg-h2-bb;
       tables 101 and 103 must remain on hub1 if healthy;
       MPLS and LTE flows must not be unnecessarily moved.

2. Complete preferred-hub isolation for one spoke

   When node1 loses all three tunnels to hub1, while hub1 remains healthy for
   node2 and node3:
       node1 must switch all three route slots to hub2;
       node1 must reach node2 through:
           node1 -> hub2 -> inter-hub -> hub1 -> node2;
       return traffic must follow:
           node2 -> hub1 -> inter-hub -> hub2 -> node1;
       hub1 must not retain a stale direct route to node1.

3. Complete hub1 failure

   When hub1 is completely unavailable:
       node1, node2 and node3 must switch all route slots directly to hub2;
       node4 and node5 must continue through hub2;
       all five spokes must retain LAN-to-LAN connectivity;
       recovery must not require acknowledgement from failed hub1.

4. Tunnel recovery and failback

   A recovered tunnel must enter RECOVERING, not immediately HEALTHY.

   Failback requires:
       multiple successful probes;
       valid WireGuard handshake;
       overlay reachability;
       SLA compliance;
       hold-down completion;
       current policy and route-state versions.

   Failback must follow the explicitly selected route-table design:

   - Baseline mode: existing and new flows remain on the backup target until
     the active cohort drains or the configured timeout expires, then the slot
     is restored atomically.
   - Enhanced mode: new flows return to the preferred target first while
     existing flows remain pinned to the backup target until they drain.

   Enhanced behavior may be claimed only when per-flow hub/target affinity and
   separate target-specific routing state are implemented and tested.

5. Flow behavior

   Ordinary SLA changes affect new flows only.
   Hard failures may remap the routing table behind an existing route slot.
   Do not reclassify established flows with nDPI.
   Do not perform per-packet load balancing.
   Preserve CONNMARK route-slot semantics during failover and recovery.

   - route ownership converges and stale ownership is rejected.

3. SaaS local breakout

   - a policy-eligible SaaS flow uses direct Broadband when healthy;
   - Broadband failure selects LTE when LTE is permitted and healthy;
   - a policy requiring hub backhaul uses the correct WireGuard hub tunnel;
   - packet captures prove that direct breakout and hub backhaul are distinct;
   - NAT is applied only to intended Internet traffic;
   - multiple clients can download the same Nginx-light test file concurrently;
   - bandwidth, delay, loss and competing traffic affect measured results;
   - the reported selected path matches the observed packet path.

4. Optional Cloud VPC

   - the original topology works when the Cloud VPC is disabled;
   - every spoke reaches the cloud application when it is enabled;
   - return-path affinity is correct;
   - cloud gateway or tunnel failure follows the implemented redundancy model;
   - recovery respects health thresholds, hysteresis and version checks;
   - no Cloud VPC private prefix is sent through direct Internet breakout.

5. Classification and policy

   - TCP, UDP, HTTP, HTTPS, DNS and optional QUIC workloads produce the
     documented classification behavior;
   - unknown and low-confidence flows use a safe administrator-defined policy;
   - nDPI metadata does not directly select the route;
   - Policy Service intent constrains Edge Agent local selection;
   - later packets restore the saved connection decision without unnecessary
     repeated DPI;
   - established-flow and new-flow behavior is tested separately.

6. Failure and restart behavior

   - classifier failure;
   - edge-agent failure;
   - Policy Service failure;
   - Ryu failure;
   - database outage and restart;
   - Broadband and LTE failure;
   - hub failure;
   - cloud-gateway failure when the optional VPC is enabled;
   - reconstruction of routes, rules, NAT, firewall and ownership from
     persistent desired state.

7. Performance and experimental evidence

   Compare at least:

   ```text
   branch -> hub -> SaaS
   branch -> direct Internet -> SaaS
   branch -> Data Center LAN
   branch -> optional Cloud VPC
   ```

   Measure, without inventing results:

   - RTT;
   - jitter;
   - packet loss;
   - throughput;
   - HTTP response time;
   - file-transfer completion time;
   - TCP retransmissions;
   - failover time;
   - CPU and memory use;
   - classification accuracy and confidence.
